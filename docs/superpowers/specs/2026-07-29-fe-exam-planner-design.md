## 0. このアプリの立ち位置（前提の確認）

- 日々の発火装置は**すでに稼働している上司への日次報告（keystone）**であり、このアプリではない。
- このアプリの仕事は **「試験日から逆算した作戦を確定させ、今日やる量を毎朝ゼロから計算して出す」** こと。
- 本人の既往ログ上、**逆算と記録/可視化は潰れた案**（`progress-engine-log.md`）。それを承知の上で「毎日開く管理アプリ」を本人が選択した。
  そのため設計側で以下のガードを入れる：
  - **未消化の「山」を作らない**（残り問数は毎朝 残り日数に溶かして均す）
  - **日別の履歴を保存しない**（保存するのは累計消化問数と模試結果のみ）
  - **達成不可能なノルマを出さない**（上限を超えたら日程変更を提案する）

## 2. 全体構成

単一HTMLファイル `fe-exam-planner.html`。サーバ不要、iPhone Safariで開く。既存の `goal-manager.html` / `garden.html` と同じ流儀。

3つの部品に分ける:

1. **エンジン（`window.Engine`）** — 純粋関数のみ。DOM・localStorageに触らない。テスト対象。
2. **ストア** — localStorage 1キー（`fe-exam-planner-v1`）にJSON1個。
3. **UI** — タブ3つ（今日／作戦／設定）。これ以上増やさない。

### 保存するデータ

```
{
  version, examDate, startDate,
  capacity: { weekday, weekend },      // 1日に解ける問数（本人申告）
  goalPerTopicA,                       // 科目A 1分野あたりの目標問数
  goalTotalB,                          // 科目B 総目標問数
  weights: { [topicId]: number },      // 出題比重（初期値は§1の概数、設定で編集可）
  consumed: { a, b },                  // 累計消化問数のみ
  topicConsumed: { [topicId]: number },
  checkpoints: [ { date, done, correctA, correctB, topicCorrect } ]
}
```

**保存しないもの: 日別の実施履歴、連続日数、達成率の推移。** 意図的に持たない（§0のガード）。

## 3. エンジン仕様

### 3-1. チェックポイント（模試）の配置

残り日数 `N = 試験日 − 開始日` で回数が決まる。

| N | 回数 | 配置 |
|---|---|---|
| N ≥ 84 | 4回 | 0, (N−7)/3, 2(N−7)/3, N−7 日目 |
| 42 ≤ N < 84 | 3回 | 0, (N−7)/2, N−7 |
| 21 ≤ N < 42 | 2回 | 0, N−7 |
| N < 21 | 1回 | 0（＋「期間が短い」と警告表示） |

- 初回は必ず **開始当日＝実力測定**。目標ラインは無い。
- 最終回は必ず **本番7日前**（立て直せる最後の地点）。

### 3-2. 各チェックポイントの必要ライン

- 基準線 `S` = 初回模試の実測正答率（科目A・Bそれぞれ）
- 本番目標 `G` = **科目A 0.75 / 科目B 0.80**
  - 合格ラインは各600/1000（≒6割が目安）。IRTで素点比例ではないためマージンを取る。
  - 科目Bは20問しかなく1問の重みが大きい＝分散が大きいので、Bのマージンを厚くする。
- 進捗率 `p = そのCPの日数 / N`
- **必要ライン = S + (G − S) × p^0.7**
  - 線形ではなく前倒し。終盤に追い上げる計画は、遅れた時に取り返す場所が残っていないため。
- `S ≥ G` の場合は必要ライン = G 固定とし、「すでに目標に届いている＝試験日を前倒しできる」と表示する。

### 3-3. 今日のノルマ

毎朝ゼロから再計算する。前日の未消化を繰り越さない（山を作らない）。

```
残り問数        = 目標総問数 − 累計消化問数
残り重み日数    = Σ(残りの各日の重み)     // 平日=1.0, 土日=weekend/weekday の比率
基準ノルマ      = 残り問数 ÷ 残り重み日数 × 今日の重み
gap            = max(0, 直近CPの必要ライン − 直近CPの実測正答率)
ギャップ係数    = 1 + gap × 3            // 未達なら増える
今日のノルマ    = 基準ノルマ × ギャップ係数
上限           = 今日の重み × capacity × 1.5
```

- `今日のノルマ > 上限` の場合、**ノルマは上限で頭打ちにし、「量では届かない」警告を出す**。
  同時に選択肢を2つ提示する: **(a) 試験日を後ろにずらす** / **(b) 目標正答率を下げる**。
  達成不可能な数字を黙って表示することはしない。
- 目標総問数を消化しきった場合は、自動で1周分（科目A: 分野数×goalPerTopicA）を加算する（2周目に入る）。

### 3-4. 分野の割り当て

- 優先度 `priority(topic) = (1 − 正答率(topic)) × 出題比重(topic)`
  - 模試で分野別の実測がまだ無い分野は、正答率 = 全体正答率（未測定なら0）として扱う。
- 今日のノルマを **優先度上位3分野**に配分する（比率は優先度の比。最低1問）。
- 科目Bは常に別枠。ノルマの約15%を科目Bに割り当てる（科目Bは20問/100分＝1問が重く、毎日少量が有効なため）。

### 3-5. 分野リストと初期比重（科目A、全23分野）

出題比重の初期値は§1の大分類の概数（テクノロジ41／マネジメント7／ストラテジ12）を分野へ割り振ったもの。**分野単位の内訳は推定であり、設定画面で編集できる。**

- テクノロジ系: 基礎理論4／アルゴリズムとプログラミング3／コンピュータ構成要素4／システム構成要素3／ソフトウェア4／ハードウェア2／ヒューマンインタフェース1／マルチメディア1／データベース4／ネットワーク5／セキュリティ6／システム開発技術3／ソフトウェア開発管理技術1（計41）
- マネジメント系: プロジェクトマネジメント3／サービスマネジメント3／システム監査1（計7）
- ストラテジ系: システム戦略2／システム企画2／経営戦略マネジメント2／技術戦略マネジメント1／ビジネスインダストリ2／企業活動2／法務1（計12）

科目B: アルゴリズムとプログラミング（20問中 約16問）／情報セキュリティ（約4問）。**この内訳も概数。**

## 4. 画面

### 4-1. 「今日」
- 本番までの日数／次のチェックポイントまでの日数と必要ライン
- 今日のノルマ（分野×問数、科目Bを含む）
- 「今日の分をやった」ボタン → 累計消化問数に加算するだけ
- 常時表示: **「1問でもやれば今日は勝ち（床）」**。ノルマ未達を失敗として表示しない。
- 模試の日は、ノルマの代わりに模試の手順（科目A 60問90分／科目B 20問100分）と結果入力欄を出す。

### 4-2. 「作戦」
- チェックポイント一覧: 日付／必要ライン／実測（済んだ回のみ）
- **ここだけが「昨日できなかったことが今日できる」が見える場所。** 日々の消化状況は見せない。

### 4-3. 「設定」
- 試験日、1日に解ける問数（平日/休日）、目標正答率、分野あたり目標問数、出題比重の編集、データ初期化

## 5. 検証方法

エンジンは純粋関数なので、HTML内の `<script id="engine">` ブロックを抽出してNodeで直接実行し、以下を検証する:

1. チェックポイント配置: N=120/60/30/14 の各ケースで回数と日付が仕様通り
2. 最終CPが常に「本番7日前」（N≥21のとき）
3. 必要ライン: p=0でS、p=1でG、途中が線形より上（前倒し）
4. `S ≥ G` のとき必要ライン = G
5. ノルマ: 未達（gap>0）でノルマが増える／上限で頭打ちになり警告フラグが立つ
6. 分野割り当て: 合計が今日のノルマと一致、正答率の低い分野が優先される

**このテストを通した出力を確認するまで「できました」と言わない。**

## 6. やらないこと（膨張ガード）

- 通知・リマインダー（自分で消せる＝漏れる）
- 連続日数・カレンダー・グラフなどの可視化
- 上司報告（keystone）との連携
- 複数試験の管理

これらは keystone が回り続け、かつ本人が明示的に求めたときに初めて検討する。
