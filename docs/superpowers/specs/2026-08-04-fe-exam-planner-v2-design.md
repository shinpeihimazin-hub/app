## 1. なぜ作り直すのか

v1は本人への確認を取らずに設計した部分が多く、ヒアリングの結果、**前提が3本のうち2本 折れた**。

| v1の骨 | v1の前提 | ヒアリング結果 | 判定 |
|---|---|---|---|
| 模試4回で実力を測る | 190分の塊を取れる | **時間を取る自信が無い** | 廃止 |
| 今日のノルマ（分野×問数） | 1日の量がほぼ一定 | **完全にバラバラ**（0問の日も20問の日もある） | 廃止 |
| 試験日から逆算して残量を配る | — | 維持。ただし配り方は作り直し | 再設計 |

v1にはこのほか実装上の欠陥があった（分野別入力が未実装のまま「弱点に寄る」と設計書に記載、模試日に開かないと永久に取りこぼす、初回を落とすと必要ラインが永久に出ない）。v2はこれらを構造的に潰す（§7）。

## 5. 全体構成

単一HTMLファイル `fe-exam-planner.html`。サーバ不要、iPhone Safariで開く。GitHub Pages（`https://shinpeihimazin-hub.github.io/app/fe-exam-planner.html`）で配信済み。

3つの部品に分ける：

1. **エンジン（`<script id="engine">` → `window.Engine`）** — 純粋関数のみ。DOM・localStorageに触らない。テスト対象。
2. **ストア** — localStorage 1キー（`fe-exam-planner-v2`）にJSON1個。**v1のキーとは別にする**（データ構造が非互換のため。v1のデータは読まない）。
3. **UI** — タブ3つ（今日／記録／設定）。これ以上増やさない。

## 6. エンジン仕様

### 6-1. 分母と残量

```
分母(科目A) = 240   // 現行制度4年分。設定で変更可
残り        = 分母 − 過去問道場から写した累計解答数
```

累計解答数が分母に達したら、分母を旧制度分へ拡張する（**+640問**）。この640問は「令和元〜4年度の旧午前＝4年×2回×80問」という**概算**であり、実際の実施回数（令和2年度春期の中止など）は確認していない。設定で編集できる。**拡張は自動で行い、画面に「2周目に入った」と表示する。**

### 6-2. 分野ごとの締切（スケジュール本体）

- 分野を**配分の大きい順**に並べる（重い分野を前に置く。後半に大物を残すと遅れた時に取り返せないため）
- 残り日数を配分比で割り、各分野に締切日を割り当てる

```
分野iの所要日数 = 残り日数 × (分野iの配分 / 残り配分合計)
分野iの締切     = 前の分野の締切 + 所要日数
```

- **締切を過ぎた分野があっても、遅れリストは作らない。** 毎回 現在日から引き直す（§7）

### 6-3. 小テスト（週1・10問）の合算

10問1回の標準偏差は `√(p(1−p)/10) ≒ 15.5pt`（p=0.6のとき）。1回の結果では判断しない。

```
推定実力 = 直近4回の合計正答数 / 直近4回の合計問数
誤差幅   = √(p(1−p)/n) × 100   [pt, 1σ]
```

| 回数 | 累計問数 | 誤差幅(1σ) | 表示 |
|---|---:|---:|---|
| 1〜3回 | 10〜30 | ±9〜15pt | 「まだ精度が足りない（あと◯回）」 |
| 4回以上 | 40以上 | ±7.7pt以下 | 「推定 ◯% ±◯pt」 |

**誤差幅は必ず併記する。** 単一の数値だけを出さない。

### 6-4. ペース判定

```
必要ペース = 残り問数 / 残り日数
実績ペース = 累計解答数 / 経過日数
過不足     = 残り問数 / 実績ペース − 残り日数   // 正なら「◯日 足りない」
```

**判定結果を出すだけで、ノルマは出さない。**「だから今日◯問やれ」は表示しない。

### 6-5. 目標正答率

本番目標は **科目A 75% / 科目B 80%**（設定で変更可）。合格は各600/1000（≒6割が目安）だが、IRTで素点比例ではないこと、科目Bは20問しかなくブレが大きいことからマージンを取る。**「75%取れば受かる」とは表示しない。**

### 6-6. 科目B（別系統）

過去問の絶対量が少ないため残り問数では測らない。**科目Bに触った日**だけを持つ（保持は直近28日、画面に出すのは**直近7日**）。目標は「週◯日触る」（初期値 週3日、設定で変更可）。

## 7. 「落としても壊れない」ための構造要件

v1の致命的欠陥を、設計として潰す。

| v1の欠陥 | v2での対処 |
|---|---|
| 模試の日に開かないと永久に取りこぼす | **特定の日に開く必要がある画面を作らない。** 小テストは「いつ入れてもよい」 |
| 初回を落とすと必要ラインが永久に出ない | **基準線という概念を廃止。** 推定実力は直近4回の合算だけで決まる |
| 未消化が積み上がる | **残量は毎回 現在日から引き直す。** 遅れリストを持たない |
| 分野別入力が未実装なのに設計書には記載 | 分野別正答率は**任意入力**として明示。入力が無くても配分は出題比重だけで成立する |

**どの日に開いても、その時点の数字が正しく出ること。** これを実装の受け入れ条件とする。

## 8. 画面

### 8-1. 「今日」
```
本番まで 62日        ※これは仮の日。まだ予約していない

残り 173問 / 240問
このペースだと 8日 足りない

いま進めるべき分野：ネットワーク（9/27まで）

```
- 目標日が仮（未予約）の場合、**常時「仮の日」と明示する**
- 指図はしない。ノルマも「今日やれ」も出さない

### 8-2. 「記録」（週1で開く想定）
- 過去問道場の**累計解答数**を写す（必須の入力経路）
- **小テスト10問の正答数**を入れる → 推定実力＋誤差幅を更新
- **分野別正答率**を写す（任意。過去問道場の無料アカウントが必要なため、無くても動く）
- 科目Bに触った日を記録（トグル1つ）

### 8-3. 「設定」
- 目標日と**仮フラグ**、分母、分野配分の編集、目標正答率、科目Bの週目標
- **.ics 書き出しボタン**
- データ初期化

## 9. .ics 書き出し

ボタン1つで `fe-plan.ics` を生成しダウンロードする（Blob + `<a download>`）。外部サービスへの通信はしない。

| 種類 | 件数 | 形式 | アラーム |
|---|---:|---|---|
| 分野ごとの締切 | 23 | 終日VEVENT「FE: セキュリティ 22問まで」 | 前日 9:00 |
| 週1の小テスト | 1（RRULEで毎週） | 15分のVEVENT | 開始時 |
| 本番／仮の目標日 | 1 | 終日VEVENT | 7日前・前日 |

**制約（画面に明記する）**：作戦を引き直して書き出し直すと、**古い予定は自動で消えない**。手で消す必要がある。これは.icsの仕様上の限界。

UID は安定させる（分野IDと目標日から生成）。同じUIDなら再取り込み時に更新される可能性があるが、**iOSでの実挙動は未確認**なので「手で消す必要がある」と案内する。

## 10. データ構造

localStorage キー `fe-exam-planner-v2`、JSON1個。

```
{
  version: 2,
  targetDate: "2026-11-05",
  provisional: true,             // 仮の目標日か（未予約か）
  startDate: "2026-08-04",
  totalA: 240,                   // 分母。拡張されると増える
  expanded: false,               // 2周目に入ったか
  weights: { [topicId]: number },// 分野配分（初期値は§4、編集可）
  answeredA: 0,                  // 過去問道場から写した累計解答数
  answeredAt: "2026-08-04",      // 最後に写した日
  quizzes: [ {date, correct, total} ],   // 直近8回まで保持（合算に使うのは直近4回。
                                         // 合算回数を設定で増やせるよう余分に持つ）
  quizWindow: 4,                         // 合算に使う回数
  topicRates: { [topicId]: 0..1 },       // 任意入力
  goal: { a: 0.75, b: 0.80 },
  bTouchedDays: [ "2026-08-03", ... ],   // 直近28日だけ保持
  bWeeklyGoal: 3
}
```

**保存しないもの**：日別の実施履歴、連続日数、達成率の推移、未達の記録。意図的に持たない。

## 11. 検証方法

エンジンは純粋関数なので、HTMLから `<script id="engine">` を抽出してNodeで実行する。**テストはリポジトリに入れる**（v1ではスクラッチパッドに置いたまま入れず、再現できなかった）。

検証項目：
1. 分野の締切：配分比どおりに日数が割り当てられ、最後の分野の締切が目標日以前に収まる
2. 締切の引き直し：現在日を変えても、常に現在日から目標日までを割り直す（遅れが蓄積しない）
3. 分母の拡張：累計解答数が分母に達すると拡張され、残りが負にならない
4. 推定実力：直近4回だけを使う、5回目以降は古い回が落ちる、3回以下では「精度不足」を返す
5. 誤差幅：n=10で±15.5pt、n=40で±7.7pt 前後になる
6. ペース：実績ペース0（まだ1問も解いていない）で0除算しない
7. .ics：23分野＋小テスト＋本番のVEVENTが生成され、DTSTART/DTEND/UID/VALARMが妥当な形式である
8. 目標日が過去・目標日が近すぎる（7日未満）場合に破綻しない

**このテストを通した出力を確認するまで「できました」と言わない。**
加えて、ブラウザで一連の操作（目標日入力→累計解答数を写す→小テスト入力→.ics書き出し）を実行して確認する。

## 13. 残る懸念（設計で解けていないもの）

正直に記録する。これらは設計で解決していない。

1. **これは逆算の道具である。** 本人のログ上、逆算（未来駆動）は実体験で潰れている。動く保証はない。
2. **アプリを開く仕掛けが中に無い。** 指図しない設計（#6）を選んだ結果、開く動機はアプリ内に存在しない。.icsの締切通知が唯一の外部からの接触になる。
3. **入力（累計解答数を写す）が止まれば、全ての数字が古くなる。** 止まったことを検知して何かする仕組みは入れていない（責める表示は作らない方針のため）。
4. **目標日が仮のままなら、外的な拘束力はゼロ。** 受験予約（handoff §5-2）は未実行のまま。アプリはその代替にならない。
