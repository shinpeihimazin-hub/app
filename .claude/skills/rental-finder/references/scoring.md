# 優先度の設計とスコアリング

物件比較の破綻は、ほぼ全て**単位が揃っていない**ことに起因する。「家賃10万で条件2つ欠け」と「家賃12万で全部充足」は、そのままでは比較できない。

このスキルは**すべてを円に換算する**ことで比較可能にする。

## 1. 3分類の定義

| 分類 | 意味 | スコアでの扱い |
|---|---|---|
| **MUST** | 1つでも欠けたら**候補から除外**。妥協の余地がない | ハードフィルタ。減点ではなく除外 |
| **WANT** | 満たせば嬉しい。満たさなくても住める | **円に換算**して実質コストに加算 |
| **NICE** | 決め手にはならないが、同点なら欲しい | 同点時のタイブレークのみ |
| **不問** | どちらでもよい | 無視 |

### 分類の判定手順（迷ったらこれで機械的に決める）

各項目について順に問う。

1. **「これが無い物件には、家賃がいくら安くても住まないか？」**
   → はい ＝ **MUST**
2. **「これを満たすなら、家賃を月いくらまで多く払えるか？」に金額で答えられるか？**
   → 答えられる ＝ **WANT**（その金額が交換レート）
3. **金額で答えられないが、あると嬉しいか？**
   → はい ＝ **NICE**
4. どれでもない → **不問**

**金額で答えられないWANTは存在しない。** 「大事だけど金額は分からない」と言われたら、それは分類が済んでいないだけなので手順1に戻す。

## 2. 交換レートの聞き出し方（ラダー法）

「いくらまで出せますか」と白紙で聞いても答えられない。**二分探索で刻む。**

> 「独立洗面台があると、月+5,000円まで出せますか？」→ はい
> 「では+10,000円なら？」→ いいえ
> 「+7,000円は？」→ はい
> → 交換レート ≒ 8,000円

3〜4回の往復で十分な精度が出る。**上位5つのWANTには必ずこれを行う。** 6位以下は重み（1〜10）だけでもよい。

### ラダー法の副作用（これが本命）

金額を刻む過程で、ユーザー自身が**「思ったより大事じゃなかった」「これは実はMUSTだった」**と気づく。分類のやり直しが発生したら、それはヒアリングが成功している証拠。歓迎して分類し直す。

## 3. 実質月額コスト（比較の基本単位）

物件ごとに、以下を計算して**低い順**に並べる。

```
実質月額コスト =
      家賃（管理費・共益費込み）
    + 初期費用の月割り        … 初期費用合計 ÷ 想定居住月数
    + 光熱費の差額            … プロパンガス等による上振れ分
    + 未充足WANTのペナルティ  … Σ（満たしていないWANTの交換レート）
    - 充足ボーナス            … 0（WANTは「満たして当然」を基準に置くため加点しない）
```

**未充足WANTを「加算」する形にするのが要点。** 「良い条件に加点」ではなく「欠けた条件を金額で埋め合わせる」と考えることで、家賃の安い物件が持つ隠れコストが表に出る。

### 想定居住月数

`TIM_short_term` と `LIF_family_plan` から決める。未回答なら **48ヶ月（4年）を仮定し、仮定した旨を明示する**。

短く見積もるほど初期費用の重みが増す。2年で出る前提なら、敷礼2ヶ月の物件は月あたり数千円の上乗せとして効いてくる。

### 計算の規律

- 計算は必ず `scripts/validate_conditions.py` および採点スクリプトで行う。**金額をLLMの暗算で出さない**
- 各物件について**計算過程を表で開示する**。合計値だけを出さない
- 推定値（光熱費差など）を使った箇所は `※推定` と明記する

## 4. MUSTの扱いと母数ゼロ対策

### MUST上限ルール

MUST が **8個を超えたら警告**を出す。理由：条件が積み上がるほど母数は乗算的に減り、実務上ゼロになる。

警告時の手順:

1. 現在のMUST一覧を提示する
2. `PRI_top3`（絶対に譲れない上位3つ）を確認する
3. **top3 以外のMUSTについて、1つずつ「WANTに降格するとしたら交換レートはいくらか」を聞く**
4. 金額が付いたものはWANTへ降格する
5. 「金額を付けられない」と言われた項目はMUSTのまま残す

**ユーザーが「それでも全部MUSTだ」と明示した場合は、警告つきでそのまま凍結する。** 判断はユーザーのものであり、こちらが勝手に降格させてはいけない。

### 母数がゼロになったとき

S4で候補ゼロだった場合、勝手に条件を緩めない。以下を提示して**ユーザーに選ばせる**。

- どのMUSTを外せば何件増えるか（1つずつ外した場合の件数を実測して示す）
- 予算をいくら上げれば何件増えるか
- エリアをどこまで広げれば何件増えるか

「〇〇を緩めておきました」は禁止。

## 5. 二次スコア（交換レートが付かない項目の扱い）

すべてのWANTに金額が付くのが理想だが、6位以下は重み（1〜10）で扱ってよい。その場合の副次スコア：

```
充足率スコア = Σ（充足したWANTの重み） ÷ Σ（全WANTの重み） × 100
```

**実質月額コストが第一基準、充足率スコアは第二基準**（コストが近接した物件の比較に使う）。2つの基準が逆の順位を出した場合は、**両方を並べて提示し、判断をユーザーに渡す**。片方を勝手に採用しない。

| 物件 | 家賃 | 違反したMUST |

| □□ | ¥112,000 | BLD_quake_std（旧耐震） |

## 仮定した値
