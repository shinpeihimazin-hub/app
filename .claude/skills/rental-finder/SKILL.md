# rental-finder — 賃貸の条件確定と物件探索

依頼: $ARGUMENTS

このスキルの基準ディレクトリ（以下 `$SKILL`）: このSKILL.mdがあるディレクトリ。`references/` と `scripts/` を持つ。
作業ファイルは `rental-work/` に置く。

## 鉄の掟（違反した出力は無効。文言のすり抜けは精神への違反）

```
凍結ゲート（S3）を通らずに物件探索は無い。
検算スクリプトを実行せずに「条件は固まった」と言わない。
金額をLLMの暗算で出さない。必ずスクリプトで計算する。
ユーザーが答えていない項目を、推測で埋めない。
```

例外を作れるのはユーザーだけ。自分で例外を認定した時点で違反。

## 絶対原則

1. **`未記入` と `不問` は別物。** 「こだわらない」は立派な回答であり記録する。「まだ聞いていない」は未記入であり、◎項目に1つでも残る限り凍結できない。
2. **条件は乗算的に母数を削る。** MUSTを増やすほど該当ゼロに近づく。だから交換レート（円換算）で優先順位を測る。
3. **勝手に条件を緩めない。** 候補ゼロなら、どれを外せば何件増えるかを示して**ユーザーに選ばせる**。
4. **「安い理由」を必ず説明する。** 相場より安い物件には理由がある（定期借家・プロパン・旧耐震・線路沿い・事故物件）。理由が不明なら「不明」と書く。
5. 取得できなかった情報は「取得失敗」と明記する。無かったことにしない。
6. 年収・勤務先・保証人の情報は審査可否の判断にのみ使う。**検索クエリや外部送信に含めない。**

## 合理化封じ表（この思考が浮かんだら停止し、手順に戻る）

| 言い訳 | 現実 |
|---|---|
| 「だいたい埋まったので探し始めよう」 | 埋まっていない項目は内見後か契約直前に必ず問題化する。手戻りは全工程で最も高い |
| 「質問が多いと嫌がられる」 | 省略ではなく**順序と下書き**で負荷を下げる。ラウンド1（生活動線）を先にやれば以降が速くなる |
| 「この人はたぶんこう考えるだろう」 | 推測は事実として記録され、後で誰も検証しない。`unknown: true` の方が100倍安全 |
| 「初期費用はだいたい家賃の5ヶ月くらい」 | 「だいたい」で予算は破綻する。スクリプトで内訳を出す |
| 「条件が厳しすぎるので少し緩めておこう」 | 緩める判断はユーザーのもの。選択肢を出すのがこちらの仕事 |
| 「MUSTが多いが本人がそう言うので黙って進める」 | 母数ゼロの警告は伝える義務がある。伝えたうえで従うのが正しい |
| 「相場は知っているので調べなくていい」 | 相場は変動する。WebSearchで取れるものを記憶で代替しない |

## 前提の確認（S0で必ず実行）

このスキルは**条件確定（S1〜S3）と物件探索（S4〜S6）で必要な装備が違う**。S1〜S3はネットワーク不要で完走できる。

## ステップ

### S0: 環境スパイク（探索を始める前に。3分で限界を見極める）

```bash
curl -m 8 -sS -o /dev/null -w "%{http_code}\n" https://suumo.jp
```

- `000` かつ `curl -sS "$HTTPS_PROXY/__agentproxy/status"` に `connect_rejected` が出る
  → **プロキシのネットワークポリシーが許可リスト外を遮断している環境**。curl/Playwright/WebFetchのどれに替えても直接取得は不可能。
- WebFetchで `403` が返る → サイト側のアンチボット。**プロキシ遮断と混同して誤診しない。**

判明した可能なルートを明示してからS1へ進む。**S4が実行不能でも、S1〜S3は必ず完走できる**ので、その旨を伝えて条件確定を先に進める。

### S1: 網羅ヒアリング（`references/interview-flow.md` を読んでから）

`references/condition-taxonomy.md` の107項目を、interview-flow のラウンド0〜7の順で埋める。

雛形の生成:
```bash
mkdir -p rental-work
python3 $SKILL/scripts/validate_conditions.py --init > rental-work/conditions.yaml
```

- 1ラウンド＝AskUserQuestion 最大4問。107問を一度に浴びせない
- **ラウンド1（生活動線）を先にやる。** ここが埋まると以降の重要度を下書きでき、ユーザーの負荷が激減する
- 各ラウンド終了時に `rental-work/conditions.yaml` へ即保存する（セッションが切れても再開できる状態を保つ）
- ○項目に仮定を置いた場合は「〜と仮定しました」と明示して確認を取る

### S2: 構造化（`references/scoring.md` を読んでから）

全項目に `rank`（MUST/WANT/NICE/不問）を付ける。WANTには `weight`（1〜10）を付ける。
上位5つのWANTには**ラダー法**で交換レート（円/月）を確定させる。

分類に迷ったら scoring.md の4段階の判定手順に機械的に従う。
**金額で答えられないWANTは存在しない。** 答えられなければMUSTかNICEであり、分類をやり直す。

### S2b: 現実性の検算（**このステップを飛ばさない**）

```bash
python3 $SKILL/scripts/validate_conditions.py rental-work/conditions.yaml
```

終了コード 0 = BLOCKなし、1 = 凍結不可、2 = 入力エラー。

検算される内容:

| 種別 | 内容 |
|---|---|
| BLOCK | ◎項目の未記入／rank未設定／WANTのweight欠落／上位5WANTの交換レート欠落 |
| WARN | MUST 8件超／初期費用が上限超過／年間家賃が年収の1/3超／二重家賃の発生／エレベーター無しで高層階／ガス種別が不問／定期借家の許容／ルームシェア |
| INFO | 初期費用の内訳／年収比率／相場照会が必要な条件／想定居住月数の仮定 |

さらに、**相場との突き合わせは WebSearch で行う**（`I5_MARKET_CHECK_NEEDED` が出たとき）。
「エリア × 間取り × 面積 × 築年数」で家賃相場を調べ、`BUD_rent_max` で該当が存在しうるかを確認する。相場を大きく下回っていれば、その事実をユーザーに提示する。

### S3: 凍結ゲート（**承認なしに通過しない**）

以下を全て満たすまでS4へ進まない。

- [ ] 検算スクリプトが **exit 0**（BLOCKゼロ）
- [ ] 全WARNをユーザーに提示し、各々について「承知のうえで進む」か「条件を直す」かの回答を得た
- [ ] 置いた仮定をすべて提示し、確認を得た
- [ ] ユーザーが明示的に「凍結してよい」と述べた

凍結したら `rental-work/conditions.yaml` を確定版として保存し、内容の要約を提示する。

### S4: 物件収集

S0で判明したルートに従う。優先順位は **公式API > Playwright実ブラウザ > 検索API/スクレイパMCP > WebSearchスニペット > WebFetch**。

**実行規律** — 一気通貫で流さない:
1. **spike-first**: まず1サイトを1回だけ実行し、物件情報が取れることを確認する
2. **1サイト＝1確認**: 「使ったツール／成功か失敗か／取れた件数」を明示してから次へ
3. **fail-fast**: 失敗したら同じツールで粘らず、1段だけ下のルートへ降りる。1サイトあたり最大2回

取得できなかったサイトは「取得失敗」と明記する。

**候補ゼロだった場合、勝手に条件を緩めない。** MUSTを1つずつ外した場合の件数を実測し、選択肢としてユーザーに提示する。

### S5: スコアリング（`references/scoring.md` に従う）

実質月額コストを算出して低い順に並べる。

```
実質月額コスト = 家賃(管理費込) + 初期費用/想定居住月数 + 光熱費差 + Σ未充足WANTの交換レート
```

MUST違反は減点ではなく**除外**。計算はスクリプトで行い、**計算過程を表で開示する**。

### S6: 提示

scoring.md の提示フォーマットに従う。必ず含めるもの:

- 実質月額コスト順のランキング（内訳を列で分解）
- **除外した物件と、違反したMUST**（見せないとユーザーは条件設定の妥当性を検証できない）
- 相場より安い物件については「安い理由」
- 仮定した値・推定値の一覧（`※推定` を明記）
- 内見時に現地で確認すべき項目（図面で分からないもの: 日当たり・騒音・匂い・携帯の電波・水圧・収納の実寸・搬入経路）

## 再開時

`rental-work/conditions.yaml` が既にあれば、S1をやり直さない。検算スクリプトを実行し、未記入とBLOCKの残りだけを埋める。

## 制約

- S1は最大8ラウンド程度で完結させる。無限に確認を繰り返さない
- 1回の提示は最大10物件。超える場合は上位のみ出し、絞り込み条件を提案する
- 契約・審査の可否は最終的に貸主と保証会社の判断であり、このスキルは保証しない。その旨を明示する
