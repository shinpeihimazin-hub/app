# Phase 0 — 調査（会社Claude Codeに貼る2枚目）

> **狙い**: リポジトリの「地図」を作る。**1文字もコードを書かせない。**
> 調査と生成を同じターンでやらせると、調査が浅いまま生成に走る。分離が品質の担保。
>
> 出力は画面ではなくファイル（`docs/ai-context/repo-map.md`）にする。
> これで Phase 1 以降を**まっさらなセッションで開始できる**——
> 調査で読んだ大量の文脈に最後まで課金され続ける事態を避けられる。

---

## 貼る内容（ここから下をコピー）

```
このセッションでは「調査」だけを行う。実装・修正・リファクタリングは一切しない。
目的は、以後のセッションでAIが手探りの探索をせずに済む「地図」を作ること。

## 絶対制約
- 書き込みを許可するファイルは docs/ai-context/repo-map.md ただ1つ。
  それ以外への Write/Edit は禁止。CLAUDE.md も作るな（それは次のセッションの仕事）。
- ネットワークアクセスは禁止（この環境では通らない。試すな）。
- git commit / push はしない。
- **確認できなかった項目は「未確認」と明記する。推測を事実として書くな。**
- コードの全文貼り付けは禁止。参照は `path/to/file.ext:42` の形式で示す。

## 進め方
大量のファイルを読む必要がある。サブエージェント機能（Task / Explore）が使えるなら、
読み取りはそちらに投げて、メイン会話には結論だけ戻すこと。
メイン会話でファイルを読み漁ると、その全文が以後ずっとコンテキストに残る。

## 調査する7項目

### 1. リポジトリ地図
トップレベルおよび主要なサブディレクトリについて、**1行ずつ**「何のための場所か」。
あわせて、アプリケーションのエントリポイント（起動の入口）を特定する。

### 2. コマンド事実 ← 最重要
以下の**正確なコマンド**を、定義元のファイルとともに特定する
（package.json / Makefile / pyproject.toml / CI設定 などを根拠にする）:
- ビルド
- テスト（全体／単体ファイルだけ流す方法の両方）
- lint
- フォーマット
- ローカル起動

それぞれの**おおよその所要時間**も書く。計測できるなら実際に流して計測してよい
（テストとlintは実行可。ビルドは時間がかかるならスキップして「未計測」と書く）。

この項目が曖昧だと、以後のセッションでAIが毎回コマンドを当てにいって時間を溶かす。

### 3. 規約の実例
命名規則・ファイル配置・エラー処理・ログ出力・テストの書き方について、
**抽象的な説明ではなく「模範となる実例の場所」を示す。**

悪い書き方: 「関数名はcamelCaseを使う」
良い書き方: 「新しいAPIハンドラを書くときは `src/api/users.ts:15` の形に倣う」

各観点につき1〜2箇所でよい。多すぎると地図が重くなる。

### 4. 地雷（触ると危ないもの）
- 自動生成ファイル（編集しても次の生成で消えるもの）
- 手で触ってはいけない設定ファイル
- DBマイグレーション等、実行順序に意味があるもの
- 秘匿情報が置かれている場所（**中身は絶対に書き写すな。パスだけ**）
- その他、壊すと影響範囲が大きい箇所

### 5. 頻出領域
`git log` の直近200コミット程度から、変更頻度の高いディレクトリ上位5〜10件を出す。
地図の重みづけに使う。

### 6. 既存の仕組み
CLAUDE.md / .claude/ 配下 / .cursorrules / .github/copilot-instructions.md 等が
既に存在するか。あれば、その内容の要点と、今回作るものと衝突しうる点を挙げる。

### 7. 環境の事実
- WebSearch / WebFetch が使えるか（**実際に試して確かめるな。設定と挙動から判断し、不明なら「未確認」**）
- settings.json の所在（プロジェクト側 / ユーザー側の両方）
- hooks が設定可能な状態か（settings.json に hooks セクションを書ける形か）
- ~/.claude/projects/ に会話ログが残っているか、`usage` フィールドが入っているか

## 出力形式
docs/ai-context/repo-map.md に、上の7項目をこの順の見出しで書く。

- 全体で**300行以内**を目安にする。これは次のセッションで読まれる資産であり、
  長すぎると読むだけでコストになる。
- 各項目は箇条書き中心。散文を書き連ねない。
- 冒頭に、作成日と「このファイルの更新責任」を1行で書く
  （コードが変わったら地図もずれる、という注意書き）。

## 報告
ファイルを書き終えたら、画面には以下だけを出す:
- 書いたファイルのパス
- 7項目のうち「未確認」で終わったものの一覧と、その理由
- 調査中に気づいた、地図に書くほどでもないが引っかかった点（あれば。無ければ「なし」）

repo-map.md の内容を画面に再掲するな。ファイルを読めば分かる。
```

## あなたが見るゲート

**ここが全体の品質を決めます。地図が雑なら、以降は全部その上に建ちます。**

| 見るもの | 落第の兆候 |
|---|---|
| 項目2（コマンド） | コマンドが書かれていない／「おそらく npm test」のような推測 |
| 項目3（規約） | 実例の`file:line`が無く、一般論だけ書いてある |
| 項目4（地雷） | 「特になし」で済まされている（大抵、何かある） |
| 「未確認」の数 | 多すぎるなら、その項目だけ追加で調べさせる |

不足があれば、**Phase 1に進まず、同じセッションで追加調査を指示してください。**
地図の修正は今が一番安い。
