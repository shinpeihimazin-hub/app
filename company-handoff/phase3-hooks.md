# Phase 3 — フック（無効設置）＋承認材料（会社Claude Codeに貼る5枚目）

> **必ず新しいセッションで貼る。**
>
> **ここだけ性質が違います。** フックは Claude Code が**コマンドを自動実行する**仕組みです。
> 未承認の自動実行を勝手に有効化すると、社内ルール上まずい可能性がある。
>
> だからこのフェーズは2つを同時に作ります:
> 1. フック本体を `.claude/hooks/` に置く。ただし **`settings.json` には登録しない（＝無効）**
> 2. 社内確認に持っていける説明資料 `docs/hook-review.md`
>
> 「AIが勝手にコマンドを実行する」と受け取られると話が止まります。
> **止め方が1行で書いてある**ことが、承認を通す上で一番効きます。

---

## このフックが何をするか（あなた向けの説明）

**スコープガード**と呼んでいるものです。

タスク開始時に、AI自身が「このタスクで書き込むファイル」を `.claude/task-scope` に宣言します。
以後、宣言していないパスへ書き込もうとすると、フックが**あなたの確認に回します**。

CLAUDE.md の規律ブロック第1条（着手前のファイル宣言）を、
**モデルの善意ではなく機構で担保する**層です。モデルは指示を無視することがある。
規律は、強制する仕組みが無いと必ず劣化します。

## 1. .claude/hooks/scope-guard.sh の仕様

PreToolUse フック（Write と Edit にマッチ）として動く。
標準入力に、実行されようとしているツール呼び出しのJSONが渡ってくる。

動作:
1. 標準入力からJSONを読む
2. プロジェクトルートは環境変数 CLAUDE_PROJECT_DIR（無ければ PWD）
3. `<プロジェクトルート>/.claude/task-scope` が**存在しなければ、何もせず終了（exit 0）**
   → スコープ宣言していない通常作業の邪魔をしない
4. JSONから書き込み先のファイルパス（tool_input.file_path）を取り出す
   取れなければ何もせず終了（exit 0）
5. パスをプロジェクトルートからの相対パスに変換する
6. `.claude/task-scope` を1行ずつ読む
   - 空行は無視
   - `#` で始まる行はコメントとして無視
   - 各行をグロブパターンとして相対パスと照合する（例: `src/*` は src 配下すべて）
   - どれかにマッチしたら、何もせず終了（exit 0）＝ 許可
7. どれにもマッチしなかったら、以下のJSONを標準出力に出して終了:

{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"ask","permissionDecisionReason":"宣言スコープ外への書き込み: <相対パス> — .claude/task-scope に宣言が無い。頼まれていない変更の可能性。承認するか、スコープ宣言の更新を指示してください"}}

### 重要な設計判断（必ずこの通りにすること）

**想定外のエラーが起きたときは、通す（exit 0）。**

理由: フックが壊れたときに業務が止まる方が、取りこぼしより高くつく。
`set -e` で異常終了させると、フックのバグがそのまま作業停止になる。

具体的には、JSONのパース失敗・ファイル読み込み失敗・想定外の入力は
すべて握りつぶして exit 0 にする。この判断は、スクリプト内にコメントで明記し、
docs/hook-review.md にも「取りこぼしがありうる」トレードオフとして書く。

### その他
- 外部ネットワークにアクセスするコードを1行も書くな
- ファイルを書き換えるコードを書くな（このフックは読むだけ）
- スクリプト先頭に、目的と使い方を5行程度のコメントで書く
- 実行権限を付ける（chmod +x）

## 2. 動作確認

settings.json に登録せずに、スクリプト単体で確認する。
テスト用のJSONを標準入力から流し込んで、期待通りの出力になるか確かめる。

確認する3ケース:
1. `.claude/task-scope` が無い状態 → 何も出力せず exit 0
2. task-scope にマッチするパス → 何も出力せず exit 0
3. task-scope にマッチしないパス → ask のJSONが出る

**テストで作った一時ファイルは消すこと。** task-scope を作ったなら消す。
確認結果（3ケースそれぞれの実際の出力）を報告に含める。

## 3. docs/hook-review.md の内容

社内のセキュリティ確認・上長確認に、これ1枚を出せば済む形にする。
以下の見出しをこの順で書く:

### このフックは何か
1〜2段落。AIが「頼まれていないファイル」を書き換えるのを、
着手時の宣言と照合して人間の確認に回す仕組み、という説明。

### 実行されるコマンドの全文
scope-guard.sh の全文を貼り、**主要な行ごとに「この行が何をするか」を注釈する。**
省略するな。読む人が全行を確認できる形にする。

### 外部通信をしないことの根拠
スクリプト内に、ネットワークアクセスを行う命令
（curl / wget / nc / ssh、および言語標準のHTTPクライアント等）が
**一切含まれていないこと**を、確認方法とともに示す。
「読み取りとパターン照合しかしていない」ことを、行単位で裏づける。

### 何を防ぐか／防がないか
- 防ぐ: 宣言外のファイルへの Write / Edit を、人間の確認に回す
- 防がない: Bash 経由のファイル操作、宣言そのものが広すぎる場合、
  上記の「エラー時は通す」設計による取りこぼし
  → **防がないものを正直に書くこと。** 過大に売り込むと信用を失う。

### 失敗時の挙動
想定外のエラー時は「通す（作業を止めない）」設計であること、
およびそう決めた理由（業務停止の方が損失が大きい）。

### 有効化の手順
settings.json に追記するJSONブロックの全文と、追記する場所。

### 停止方法
**settings.json から該当ブロックを削除するだけで即座に無効になる**こと。
再起動やアンインストールは不要。この1行を目立たせる。

### 導入範囲
このリポジトリのみ。他プロジェクト・他メンバーには影響しないこと。

## 承認を取りにいくときの順序

1. `docs/hook-review.md` を自分で通読する。**自分が説明できない仕組みを申請に出さない**
2. 「防がないもの」の節が正直に書けているか確認する。ここを盛ると後で崩れる
3. 出す相手を選ぶ。まずOJTトレーナー（上長）に「こういうものを入れたい」と口頭で。
   セキュリティ部門に直接投げる前に、上長を通した方が話が早い場合が多い
4. 断られたら、そこで止める。**A（CLAUDE.md）とB（サブエージェント）だけでも効果は出ます。**
   Cは上乗せであって、前提ではありません
